## 一、识别事件与内容类型

先确认“谁在什么时候做了什么、处于提议、测试、合并、发布、修复还是复盘阶段”，再从以下 8 类中选最贴近的一类：

- `kernel_release`：主线、RC、stable/LTS、linux-next 或合并窗口结果
- `security_fix`：内核漏洞、CVE、利用、缓解与修复
- `subsystem_change`：调度、内存、文件系统、网络、BPF、虚拟化等子系统变化
- `driver_update`：驱动、新硬件或架构支持
- `performance`：有测量方法的性能、功耗、可靠性或回归
- `distro_kernel`：发行版内核分支、补丁、配置、支持周期及与上游的差异
- `community_governance`：维护者变动、maintainer sign-off、开发流程、LPC 或 Kernel Summit 的治理决定
- `technical_article`：有明确方法、证据或复现路径的内核深度解读

## 二、按五轴独立打 0–10 整数分

1. `sig` 实质份量：对内核开发者、维护者或发行版工程师是否构成重要变化，而非日常脚注。
2. `nov` 信息增量：是否带来明确的新事实、结论、方法、影响范围或决策。
3. `cred` 证据强度：材料内部是否给出提交、版本、测量、议程、正式决定或可核对原文；官方身份只证明其做了声明。
4. `reson` 共振面：影响多少内核开发、运维、安全、发行版或硬件读者。
5. `act` 可用性：读者能否据此升级、回退、复现、审查补丁、调整配置或学习方法。

## 三、按内容类型加权

内部计算 `attentionScore = sig×w1 + nov×w2 + cred×w3 + reson×w4 + act×w5`。每行权重之和为 10，结果自然位于 0–100。

不要先求平均，不要改权重，不要为了靠近想象中的门槛调整结果。

## 必须正常评价的价值

- 已确认利用、可远程利用、可本地提权，或明确影响广泛版本/LTS 的内核安全问题。
- 已正式合并的重要功能、重大子系统改动、新架构或广泛硬件支持。
- 有明确数据、环境和可复现方法的性能回归或优化。
- 发行版内核分支中影响上游兼容、支持周期、安全回移或大量用户的明确变化。
- 已作出的重大治理决定、维护者职责变更或 maintainer sign-off 规则变化；LPC/Kernel Summit 只有议程时按其具体技术或治理内容评价，不因会议名自动高分。
- 技术文章给出可核对证据、分析步骤或复现方法时，按其可迁移知识评价，不因篇幅长自动加分。

## 必须压住或拦截的噪声

- 无结论的邮件列表争论：`sig ≤ 2`。
- 补丁 v2/v3 等日常迭代：`sig ≤ 3`，除非核心设计或用户影响明确变化。
- 重复 CI/回归报告、普通 stable 回移：`sig ≤ 3`。
- 无明显用户或上游影响的发行版小修：`sig ≤ 4`。
- 没有环境、数据或方法说明的跑分：`sig ≤ 3` 且 `nov ≤ 2`。
- 营销稿、厂商软文、会议报名和纯日程提醒：`sig ≤ 2`。
- 泛 Linux 教程、桌面教程、社区八卦和人事流言应由预筛 BLOCK；若误入评分，`sig = 0`、`nov = 0`、`reson = 0`。
- 同一事件的重复转载没有新信息时，不因来源数量抬分，后续由归组去重。
